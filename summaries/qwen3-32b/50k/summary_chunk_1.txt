### **Microservice Decomposition Recommendations**

#### **1. Current Monolithic Assumptions & Candidates**
The current application is not decoupled into microservices. `OrderService` and `IntegrationService` appear tightly bound, as does `Clients` to `OrderService`.

#### **2. Potential Microservice Candidates**
- **Catalog Service**:
  - *Reason*: Catalog items are independent of other order logic. Could be exposed as a standalone API.
  - *Responsibility*: Manage `description`, `price`, `inventory`, `unitPrice` for SKUs.
  - *Current Code*: `src/Backend/OrderService/models/mrp/CatalogItem.java`, `MongoCatalogItemsRepository.java`.
- **Order Processing Service**:
  - *Reason*: Heavy usage of `Order.java`, `OrderRepository.java`, and scheduling APIs. Can be split as dedicated microservice.
  - *Responsibility*: Track order creation, updates, fulfillments, and events (e.g., `OrderEventInfo.java`).
- **Quote Service**:
  - *Reason*: Handles customer quotes independently (validity rules, dealer linking).
  - *Responsibility*: Generate quotes, validate dealer info, and log quote items.
- **Shipment Service**:
  - *Reason*: Shipment tracking and delivery status can be separated from order logic.
  - *Responsibility*: Manages `ShipmentEventInfo.java`, dealer/customer delivery addresses.
- **Integration Gateway Service**:
  - *Reason*: Bridges with external systems (e.g., **Parts Unlimited Website**, external ERP systems).
  - *Current Candidates for External Comm*: `MrpConnectService.java`, scheduled job logic.
  - *Responsibility*: Expose internal events to external systems using REST or message queues (e.g., RabbitMQ or Kafka).

#### **3. Infrastructure Decomposition Notes**
- **Database Isolation**:
  - Split `MongoDB` into dedicated collections per service (e.g., `catalogdb`, `shipmentsdb`) for autonomy.
- **Orchestration via Docker**:
  - Build per-microservice Dockerfiles.
  - Use Docker Compose for local testing to simplify dependencies (Mongo, Apache, Java services).
- **ARM Template Refactoring**:
  - Build isolated templates for each microservice's VM and database (promoting **Infrastructure modularization**).
  - Use **DNS routing** to distinguish services (e.g., `catalog.mrp.azure`, `order.mrp.azure`).
