```http
POST    /api/orders/{id}/events                  // Log event (e.g., shipment confirmation)
```


## **4. Service Dependencies and Communication Patterns**

### **Internal Communication**
- **OrderService ↔ QuoteService**:
  - RESTful API for quote validation and order conversion.
  - Example: `GET /api/quotes/{id}` before creating an order.
- **OrderService ↔ DealerService**:
  - REST call to fetch dealer address and inventory constraints.
- **IntegrationService ↔ MRP System**:
  - REST/HTTP for order creation and product updates.
  - `MrpConnectService` uses `RestTemplate` for MRP integrations.

### **Event-Driven Patterns**
- **OrderLifecycle**:
  - Order status changes (e.g., `Created` → `Confirmed`) are published to `orders` queue.
  - IntegrationService listens to orders queue for background processing.
- **Shipments Tracking**:
  - Delivery events are pushed to `shipping` queue for asynchronous update propagation.

### **Message Queues (Azure)**  
- **Azure Storage Queues**:
  - **Orders Queue**: For asynchronous order creation and validation.
  - **Inventory Queue**: For background updates during product replenishment.

## **5. Business Logic and Validation Rules**

### **Order Validation Rules**
- Orders must reference an existing quote.
- Order status transitions are validated by `OrderController`.
  - `Created` → `Confirmed` → `Shipped`.
- Shipment creation requires a valid delivery date and address.

### **Quote Rules**
- Quotes must have at least one item and valid dealer/customer name.
- Total cost is calculated based on quoted items and dynamic discounts.

### **Inventory Management**
- `leadTime` and `inventory` fields in catalog items determine order fulfillment timelines.
- Low inventory triggers alerts to DealerService via `QueueFactory`.

### **Address Handling**
- Google Maps API validates dealer and delivery addresses.
- Invalid addresses are flagged in `ShipmentRecord` (`invalidAddress: boolean`).

## **8. Architectural Patterns and Design Practices**

| **Pattern**              | **Implementation**                                                                                   | **Business Need Satisfied**                                                                 |
|---------------------------|-----------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| **Microservices**         | Separation of OrderService, QuoteService, CatalogService into distinct services.                    | Independent scaling and deployment of modules like inventory and order fulfillment.         |
| **Event-Driven**          | Use of Azure Queues for order/shipping events and background processing.                            | Resilient background processing and decoupling of services.                               |
| **API Gateway**           | Web Frontend interacts with services via a unified REST API endpoint (e.g., `127.0.0.1:8080`).        | Consistent UI integration with backend services without exposing system complexity.       |
| **Infrastructure as Code** | ARM templates, Ansible playbooks, and Puppet scripts.                                               | Repeatable deployment and system consistency across environments.                         |
| **Repository Pattern**    | `CatalogItemsRepository`, `QuoteRepository`, and `OrderRepository` abstract database access.      | Loose coupling between business logic and database (supports memory/MongoDB backends).       |
| **Domain-Driven Design**  | Clear domain boundaries (e.g., `Dealers` with map integration, `Orders` tracking workflow).         | Structured modularization aligned with business workflows.                                |

## **9. Microservice Decomposition Recommendations**

### **9.1 Candidate Microservices**
| **Service Name**       | **Responsibilities**                                                                 | **Communication Mechanism**                                     | **Proposed Endpoints**                                                   |
|------------------------|--------------------------------------------------------------------------------------|-------------------------------------------------------------------|-------------------------------------------------------------------------|
| **CatalogService**     | Manages product inventory, pricing, and lifecycle.                                   | REST API, Azure Queue (for inventory updates)                    | `GET /api/catalog`, `POST /api/catalog/{sku}`, `PUT /api/price/{sku}`  |
| **QuoteService**       | Handles quote creation, validation, and conversion to orders.                        | REST API with JWT-based authentication (if enabled)              | `GET /api/quotes`, `POST /api/quote`, `DELETE /api/quote/{id}`         |
| **OrderService**       | Manages order creation, status updates, and delivery tracking.                         | REST API, Event Queue for order lifecycle events                   | `GET /api/orders`, `POST /api/order`, `PUT /api/order/{id}/status`     |
| **DealerService**      | Maintains dealer database, regional constraints, and address validation.               | REST API for dealer lookup, Google Maps integration for location | `GET /api/dealers`, `PUT /api/dealer/{id}/address`                     |
| **ShipmentService**    | Tracks shipment status, delivery dates, and event logging.                             | REST API, Event Queue for update propagation                       | `GET /api/shipments`, `POST /api/shipping/{orderId}`                   |
| **MessageBroker**      | Abstracts message passing between microservices using Azure Queues / Kafka.            | AMQP/REST over Azure Storage Queues                               | Not standalone (integrated into service meshes).                       |
| **ConfigurationService** | Centralizes application configuration (e.g., MongoDB connection strings, API keys).  | gRPC/REST API                                                       | `GET /config/database`, `GET /config/secrets`                          |

### **9.2 Service Boundaries and Decoupling**
- **QuoteService** decoupled from OrderService via asynchronous queue processing.
- **DealerService** separated from OrderService to avoid tight coupling on address validation.
- **CatalogService** independently updatable to allow dynamic pricing strategies.

### **9.3 Event-Driven Architecture**
- Event-driven communication between:
  - **QuoteService → OrderService**: Quote confirmation triggers order creation.
  - **OrderService → ShipmentService**: Shipment date propagation after order confirmation.
  - **ShipmentService → EventService**: Audit logging of delivery events.

### **9.4 Containerization Strategy**
- Each microservice containerized with `Dockerfile`s:
  - **OrderService Container**: `Dockerfile` builds WAR file and runs it in Tomcat.
  - **QuoteService Container**: `Dockerfile` wraps JAR files with embedded Jetty.
- Shared Infrastructure containers:
  - **MongoDB**: Handles catalog and dealer databases.
  - **Application Insights Agent**: Injects telemetry into all containers.

### **9.5 Observability and Monitoring**
- Centralized logging and metrics using Application Insights.
- End-to-end tracing across services via HTTP headers.
- Dockerized metrics dashboards (e.g., Prometheus for container health).
