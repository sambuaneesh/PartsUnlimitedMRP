## **1. Current Architecture Overview**

### **1.1 System Components**
| **Category**              | **Components**                                                                 |
|---------------------------|--------------------------------------------------------------------------------|
| **Core Backend Services**  | OrderService (Spring Boot), IntegrationService, Dealers/Quotes/Shipments APIs  |

| **External Integrations**  | Google Maps API (Address Lookup), Azure Application Insights (Telemetry)        |

---

### **1.2 Current Monolithic Structure**
- **Tightly Coupled Endpoints**:
  - OrderService contains order, quote, dealer, and shipment models in the same data store (MongoDB).
  - Dealers, orders, and shipments are interdependent and share domain logic.
- **Single WAR Deployment**:
  - Deployed via `mrp.war` to Tomcat with embedded Spring Boot.
- **Monorepo Setup**:
  - Shared repositories for all services (order, quote, dealer) in the same service.

## **3. Data Models and Schemas**

### **3.1 Core Data Models**
| **Model**               | **Fields/Attributes**                                                                                                                                                                                                                     |
|-------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **CatalogItem**         | `skuNumber`, `description`, `price`, `inventory`, `leadTime`, `Dimensions` (height/width/depth).                                                                                                                                          |
| **Dealer**              | `name`, `contact`, `address`, `email`, `phone`.                                                                                                                                                                                           |
| **Quote**               | `quoteId`, `dealerName`, `customerName`, `quoteItems`, `totalCost`, `discount`, `validUntil`, `purpose` (e.g., fridge/freezer), `terms`, `unitDescription`, `shippingMethod`.                                                               |
| **Order**               | `orderId`, `__quote` (FK), `status` (e.g., `Created`, `Shipped`), `orderDate`, `events` (audit log).                                                                                                                                        |
| **Shipment**            | `orderId`, `__order` (FK), `deliveryDate`, `deliveryAddress`, `contactName`, `deliveryNotes`, `deliveryMethod`.                                                                                                                          |
| **OrderEvent**          | `eventId`, `orderId`, `date`, `comment` (e.g., "Truck dispatched", "Waiting for payment").                                                                                                                                                |

### **3.2 Cross-Service Dependencies**
- **Order ↔ Quote**:
  - Order uses `quoteId` as foreign key.
  - Quote validation before order creation must pass (no duplicate references).
- **Shipment ↔ Order**:
  - Shipment is created from an order (`__order` FK).
  - Shipment status updates modify the order's life cycle (triggering events).
- **Catalog ↔ Order**:
  - Order items reference `skuNumber` from catalog.

### **7.2 Deployment and Scaling**
- **Containers**:
  - Each service becomes a Docker container.
  - Use Kubernetes for orchestration (if production).
- **Service Mesh**:
  - Enforces service discovery, circuit breakers, and fault tolerance (Istio/Linkerd).
- **Data Stores**:
  - Use per-service databases (e.g., QuoteService → MongoDB, OrderService → PostgreSQL).
  - Avoid shared databases for stronger decoupling.

## **9. Critical Technical Debt**
| **Issue**                | **Description**                                                                                                                             |
|--------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| **Tight Coupling**       | Order and Quote models are co-located; no clear service boundary.                                                                           |
| **Shared DB Schema**     | Current MongoDB stores all models in one schema; lack of service-specific DBs.                                                              |
| **No Asynchronous Flow** | Order/shipment updates are synchronous; could fail under high load.                                                                         |
| **Monorepo Limitations** | All services coexist in one repo; not conducive to team ownership and scaling.                                                             |

## **10. Summary of Opportunities**

| **Area**                  | **Opportunity**                                                                                                                             |
|--------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| **Decomposition**        | Split into 3–4 microservices with clear boundaries and data ownership.                                                                     |
| **Testability**          | Each service can be unit/integration-tested independently with mocking.                                                                    |
| **Scalability**          | Scale independently (e.g., Orders during peak, Quotes during slow periods).                                                                 |
| **Deployment Speed**     | Faster deployments, independent of other services.                                                                                         |
| **Team Autonomy**        | Frontend/backend teams can work independently without blocking each other.                                                                 |
| **Monitoring**           | Granular telemetry with service-specific logs, metrics, traces.                                                                            |
