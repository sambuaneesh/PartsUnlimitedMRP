
# Comprehensive Architectural Summary: Parts Unlimited MRP Application

## Executive Overview

Parts Unlimited MRP is a Java-based Manufacturing Resource Planning application representing a fictional outsourced MRP system inspired by "The Phoenix Project". This three-tier architecture application demonstrates a monolithic design with clear service boundaries, built on open-source technologies with comprehensive deployment automation for both cloud and on-premises environments.

**Key Characteristics:**
- **Architecture Style**: Three-tier monolith with emergent microservice boundaries
- **Primary Technology Stack**: Java 8, Spring Boot, MongoDB, WinJS
- **Deployment Platforms**: Traditional VM, Docker Containers, Azure Stack
- **Infrastructure Automation**: ARM Templates, Ansible, Chef, Puppet
- **Target for Decomposition**: Order Processing, Catalog Management, Dealer Operations, Integration Layer

## Backend Services Deep Dive

### 1. Order Service (`src/Backend/OrderService/`)

**Technology Stack:**
- Java 8, Spring Boot, Gradle
- Application Insights for telemetry
- Configurable persistence (In-Memory/MongoDB)

**Core Controllers:**

| Controller | Endpoints | Primary Responsibilities |
|------------|-----------|-------------------------|
| `DealerController` | GET/POST/PUT/DELETE `/dealers`, `/dealers/{name}` | Dealer CRUD operations with contact management |
| `OrderController` | GET/POST/PUT/DELETE `/orders`, `/orders/{id}`, `/orders/{id}/events`, `/orders/{id}/status` | Order lifecycle, event tracking, quote-to-order conversion |
| `QuoteController` | GET/POST/PUT/DELETE `/quotes`, `/quotes/{id}`, `/quotes?name={customerName}` | Quote management with customer-specific searches |
| `ShipmentController` | GET/POST/PUT/DELETE `/shipments`, `/shipments/{id}`, `/shipments/deliveries`, `/shipments/{id}/events` | Delivery tracking and shipment aggregation |
| `CatalogController` | GET/POST/PUT/DELETE `/catalog`, `/catalog/{skuNumber}` | Product catalog and inventory management |
| `PingController` | HEAD/GET `/ping` | Health checks and build metadata |

**Repository Architecture:**
- **Pattern**: Repository Pattern with Factory selection
- **Implementations**: 
  - In-memory (`Mock*Repository`) for testing
  - MongoDB (`Mongo*Repository`) with retry logic
- **Factory**: `RepositoryFactory` abstracts storage selection via `application.properties`

**Key Business Logic:**
- Quote-to-Order conversion with immutable quote data
- Order status progression: Created → Confirmed → Started → Built → Shipped → Delivered
- Shipment event tracking with validation
- Catalog inventory management with lead time calculations

### 2. Integration Service (`src/Backend/IntegrationService/`)

**Technology Stack:**
- Java 8, Spring Boot, Azure Storage SDK
- Jackson for JSON processing

**Core Components:**
- `MrpConnectService`: External system connectivity
- `QueueService`: Azure Queue Service operations
- Scheduled Tasks:
  - `CreateOrderProcessTask`: Periodic order processing
  - `UpdateProductProcessTask`: Inventory synchronization

**Data Transformation:**
- Website Order Messages → MRP Order entities
- Product Updates → Catalog synchronization
- Queue-based asynchronous processing

**External Dependencies:**
- Azure Queue Service
- Parts Unlimited Website REST API
- MRP System REST API

### Data Relationships and Constraints

**Primary Relationships:**
- Quote → Order (1:1, immutable reference)
- Order → Shipment (1:1)
- Quote → Dealer (N:1 via dealerName)

- Required field validation across all entities

## API Contracts and Communication Patterns

### REST API Specification

**Base Configuration:**
- Content-Type: `application/json`
- Standard HTTP Methods: GET, POST, PUT, DELETE
- Status Codes: 200 (OK), 201 (Created), 204 (No Content), 400 (Bad Request), 404 (Not Found), 409 (Conflict)

**Complete API Endpoints:**

```
// Catalog Management
GET    /catalog                    // List all catalog items
POST   /catalog                    // Add new catalog item (SKU uniqueness enforced)
PUT    /catalog/{skuNumber}        // Update catalog item
DELETE /catalog/{skuNumber}        // Remove catalog item

// Dealer Management
GET    /dealers                    // List all dealers
POST   /dealers                    // Add new dealer
PUT    /dealers/{name}              // Update dealer (name as identifier)
DELETE /dealers/{name}              // Remove dealer

// Quote Management
GET    /quotes                     // List all quotes
GET    /quotes?name={customerName}  // Get quotes by customer
POST   /quotes                     // Create new quote
PUT    /quotes/{id}                // Update quote
DELETE /quotes/{id}                // Delete quote

// Order Management
POST   /orders                     // Create new order
POST   /orders?fromQuote={id}      // Create order from existing quote
GET    /orders/{id}                // Get order by ID
PUT    /orders/{id}/status         // Update order status
POST   /orders/{id}/events         // Add order event
DELETE /orders/{id}                // Delete order

// Shipment Management
GET    /shipments                  // List all shipments
GET    /shipments?status={status}  // Filter by status
POST   /shipments                  // Create new shipment
PUT    /shipments/{id}             // Update shipment
POST   /shipments/{id}/events      // Add shipment event
GET    /shipments/deliveries       // Aggregate delivery data (Quote+Order+Shipment)
DELETE /shipments/{id}             // Delete shipment

// Health Check
HEAD   /ping                       // Service health check
GET    /ping                       // Service health check with metadata
```

### Communication Patterns

**Synchronous Communication:**
- Frontend → Order Service: Direct REST API calls
- Order Service → MongoDB: Direct database operations
- Integration Service → MRP System: REST API integration

**Asynchronous Communication:**
- Integration Service → Azure Queue: Message-based processing
- Scheduled Task Processing: Periodic batch operations
- Queue-based order processing pipeline

**Error Handling:**
- Centralized error reporting via `TelemetryClient` (Application Insights)
- HTTP status code standardization
- Validation error aggregation with detailed responses

## Infrastructure and Deployment

### Deployment Architecture Options

#### 1. Traditional VM Deployment
**Configuration:**
- Ubuntu Server 14.04/16.04
- Java 8 JRE/JDK
- Apache Tomcat 7 (custom port 9080)
- MongoDB
- Open Ports: 22 (SSH), 9080 (MRP), 8080 (Order Service)

**Infrastructure Requirements:**
- VM Size: Standard_A2 (2 Cores, 3.5GB RAM)
- Network: 10.0.0.0/16 VNET
- Storage: Standard_LRS

#### 2. Docker Containerization
**Service Architecture:**
```yaml
services:
  database:
    image: mongo
    ports:
      - "27017:27017"    # MongoDB
      - "28017:28017"    # HTTP UI
    volumes:
      - ./MongoRecords.js:/docker-entrypoint-initdb.d/init.js
    
  order-service:
    build: ./Backend/OrderService
    ports:
      - "8080:8080"
    links:
      - database:mongo
    
  web-client:
    build: ./src/Clients
    ports:
      - "9080:8080"
    depends_on:
      - order-service
```

#### 3. Azure Stack Integration
**Available Templates:**

## Microservice Decomposition Analysis

### Natural Service Boundaries

#### 1. Catalog Service
**Responsibilities:**
- Product information management
- Inventory tracking and updates
- Pricing management
- Lead time calculations

**Data Ownership:**
- `catalog` collection
- SKU-based indexing

**API Surface:**
- Full CRUD on catalog items
- Inventory queries
- Price update endpoints

#### 2. Dealer Service
**Responsibilities:**
- Dealer information management
- Contact details maintenance
- Location data with geocoding

**Data Ownership:**
- `dealers` collection
- Address validation via Google Maps integration

**API Surface:**
- Dealer CRUD operations
- Location-based searches
- Contact information updates

#### 3. Quote Service
**Responsibilities:**
- Quote generation and lifecycle management
- Customer-specific pricing
- Expiration tracking

**Data Ownership:**
- `quotes` collection
- Quote-item relationships

**API Surface:**
- Quote CRUD operations
- Customer-based searches
- Quote-to-order conversion preparation

#### 4. Order Service
**Responsibilities:**
- Order lifecycle management
- Status progression tracking
- Event logging

**Data Ownership:**
- `orders` collection
- Order event history

**API Surface:**
- Order CRUD operations
- Status updates
- Event tracking

#### 5. Shipment Service
**Responsibilities:**
- Delivery tracking and coordination
- Shipment event management
- Delivery address validation

**Data Ownership:**
- `shipments` collection
- Shipment event history

**API Surface:**
- Shipment CRUD operations
- Event tracking
- Delivery status queries

#### 6. Integration Service (Already Separated)
**Responsibilities:**
- External system integration
- Queue-based message processing
- Data synchronization

**Data Ownership:**
- Transient message data
- Integration state tracking

### Inter-Service Communication Patterns

**Synchronous Calls:**
- Order Service → Quote Service (for order creation from quote)
- Shipment Service → Order Service (for shipment validation)
- Frontend → Multiple services via API Gateway

**Asynchronous Communication:**
- Event-driven status updates (e.g., Order Status → Shipment Events)
- Inventory synchronization events
- Notification events (future enhancement)

**Data Consistency Strategies:**
- Saga pattern for quote-to-order-to-shipment flow
- Eventual consistency for inventory updates
- Distributed transaction coordination where required

### Database Decomposition Strategy

**Service-Specific Databases:**
- Each service owns its MongoDB database/collection
- Cross-service queries handled via API composition
- Data synchronization for relationships maintained via events

**Migration Considerations:**
- Gradual extraction using database-per-service pattern
- Shared databases during transition period
- API compatibility layers maintained during migration

### Deployment Evolution Path

**Phase 1: Service Separation**
- Extract existing controllers into separate Spring Boot applications
- Maintain database sharing initially
- Implement service discovery via configuration

**Phase 2: Database Separation**
- Migrate to service-specific databases
- Implement cross-service data synchronization
- Add distributed tracing and monitoring

**Phase 3: Advanced Patterns**
- Implement API Gateway for frontend routing
- Add circuit breakers and bulkheads
- Implement event-driven architecture where appropriate

### Technical Considerations

**Frontend Migration:**
- Implement BFF (Backend-for-Frontend) pattern
- Update service endpoint configuration
- Consider micro-frontend architecture for complex pages

**Monitoring and Observability:**
- Extend Application Insights across all services
- Implement distributed tracing
- Add service health checks and metrics

**Configuration Management:**
- Externalize service-specific configurations
- Implement configuration service
- Add feature flags for gradual rollout

**Security Enhancements:**
- Implement service-to-service authentication
- Add API rate limiting
- Secure inter-service communication

### Critical Dependencies and Risks

**High-Risk Areas:**
- Quote-to-order transaction integrity
- Shipment-to-order data consistency
- Frontend tightly coupled to monolithic endpoint

**Mitigation Strategies:**
- Implement comprehensive integration testing
- Use feature flags for gradual migration
- Maintain backward compatibility during transition
- Implement canary deployments for critical services

This architectural analysis reveals a monolithic application with clear service boundaries that can be methodically decomposed into microservices while maintaining business continuity and system reliability.
