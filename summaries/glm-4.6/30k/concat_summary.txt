# Architectural Summary: Parts Unlimited MRP Application

## Overview
Parts Unlimited MRP is a Java-based Manufacturing Resource Planning application built on open-source technologies, designed as a fictional outsourced MRP system. The application demonstrates a three-tier architecture with web frontend, backend services, and MongoDB database, along with comprehensive deployment automation for cloud and on-premises environments.

## Core Components

### 1. Backend Services

#### 1.1 Order Service (`src/Backend/OrderService/`)
- **Technology Stack**: Java 8, Spring Boot, Gradle
- **Primary Database**: MongoDB
- **Responsibilities**: 
  - Order management lifecycle
  - Quote generation and management
  - Catalog item management
  - Dealer information management
  - Shipment tracking
- **API Endpoints** (via controllers):
  - `/catalog` - Product catalog operations
  - `/dealers` - Dealer management
  - `/orders` - Order CRUD operations
  - `/quotes` - Quote operations
  - `/shipments` - Shipment tracking
  - `/ping` - Health check

#### 1.2 Integration Service (`src/Backend/IntegrationService/`)
- **Technology Stack**: Java 8, Gradle
- **Responsibilities**:
  - Integration with external Parts Unlimited Website
  - Asynchronous order processing
  - Product data synchronization
  - Queue management for message handling
- **Key Components**:
  - `MrpConnectService`: External system connectivity
  - `QueueService`: Message queue operations
  - Scheduled tasks for periodic processing
  - Models for MRP entities (Order, Quote, Shipment, etc.)

### 2. Frontend (`src/Clients/`)
- **Technology Stack**: HTML5, CSS3, JavaScript, Apache Tomcat
- **Deployment**: WAR file deployed to Tomcat
- **Pages/Modules**:
  - Main dashboard
  - Catalog browsing
  - Order management
  - Quote management
  - Dealer information
  - Delivery tracking
  - Order events tracking

### 3. Database Layer
- **Database**: MongoDB
- **Key Collections**:
  - `catalog`: Product items with pricing, inventory, lead times
  - `dealers`: Dealer contact information
  - `quotes`: Price quotes with validity dates
  - `orders`: Order status and details
  - `shipments`: Delivery information and tracking

## Data Models

### Core Entities
1. **CatalogItem**: Product information, pricing, inventory levels
2. **DealerInfo**: Dealer contact details
3. **Order**: Order details, status, associated quotes
4. **Quote**: Price quotes with validity periods
5. **ShipmentRecord**: Shipping information and events
6. **DeliveryAddress**: Delivery location details
7. **PhoneInfo**: Contact phone numbers

## Communication Patterns

### 1. Service Communication
- **Frontend → Order Service**: REST API calls
- **Order Service → MongoDB**: Direct database operations
- **Integration Service → External Systems**: Queue-based messaging

### 2. Asynchronous Processing
- Queue-based order processing
- Scheduled tasks for:
  - Order creation (`CreateOrderProcessTask`)
  - Product updates (`UpdateProductProcessTask`)

## Configuration Management

### Application Configuration
- **Order Service**: `application.properties`
- **Integration Service**: `application.properties`
- Environment-specific configurations via properties files

### Infrastructure as Code
- **Azure Resource Manager** templates for cloud deployment
- **Chef** cookbooks for configuration management
- **Puppet** manifests for infrastructure provisioning
- **Ansible** playbooks included in lab files

## Deployment Architecture

### Deployment Options
1. **Traditional VM Deployment**:
   - Ubuntu Server (14.04/16.04)
   - Tomcat 7 on port 9080 (customized from default 8080)
   - Java 8 JRE/JDK
   - MongoDB

2. **Docker Containerization**:
   - Separate containers for:
     - Frontend (Client)
     - Database (MongoDB)
     - Order Service
   - Build scripts in `deploy/docker/`

3. **Azure Stack Integration**:
   - VM templates for:
     - Chef Server/Workstation
     - Jenkins CI/CD
     - Puppet Enterprise
     - MRP Application base

### CI/CD Pipeline
- **Build System**: Gradle
- **CI**: Travis CI configuration
- **Artifact Management**: JAR files for services, WAR for frontend
- **Deployment Scripts**: Shell scripts for automated deployment

## Security Considerations
- Network Security Groups (NSGs) defined in Azure templates
- SSH key-based authentication for VM access
- HTTPS endpoints for secure communication (443, 8443)
- Application Insights integration for monitoring

## External Integrations
- Integration with Parts Unlimited Website via Integration Service
- Queue-based messaging for asynchronous operations
- Support for configuration management tools (Chef, Puppet)

## Business Logic Summary
1. **Order Processing Flow**:
   - Quote generation → Order creation → Status tracking → Shipment
2. **Inventory Management**:
   - Catalog item tracking with inventory levels
   - Lead time calculations
3. **Dealer Management**:
   - Multiple dealers with contact information
   - Quote generation per dealer
4. **Delivery Tracking**:
   - Shipment events and status updates
   - Delivery address management

## Development Frameworks
- **Backend**: Spring Boot, Gradle
- **Frontend**: Plain JavaScript (no framework identified)
- **Testing**: JUnit for backend services
- **Build**: Gradle wrapper for consistent builds
- **Deployment**: Custom shell scripts and ARM templates

This architecture represents a monolithic application with clear separation between frontend, backend services, and database, making it a good candidate for microservice decomposition by extracting the Order and Integration services as independent microservices with their own databases or bounded contexts.

### Comprehensive Architectural Summary for Microservice Decomposition

#### **1. Core Components & Responsibilities**
- **Controllers**:
  - `DealerController`: CRUD operations for dealers (`/dealers`). Includes intentional performance testing loop (100k MongoDB calls).
  - `OrderController`: Manages orders (`/orders`). Handles order creation (from quotes), status updates, and event tracking.
  - `QuoteController`: Quote lifecycle management (`/quotes`). Supports CRUD and customer-based searches.
  - `ShipmentController`: Shipment logistics (`/shipments`). Tracks delivery status and aggregates delivery data (Quote + Order + Shipment).
  - `PingController`: Health checks (`/ping`). Returns service status and build metadata.

- **Models**:
  - **Core Entities**: `Order`, `Quote`, `ShipmentRecord`, `DealerInfo`, `CatalogItem`.
  - **Supporting Models**: `DeliveryAddress`, `PhoneInfo`, `OrderEventInfo`, `ShipmentEventInfo`.
  - **Enums**: `OrderStatus` (tracks order state from `Created` to `Installed`).
  - **Validation**: Each model includes `validate()` methods with error aggregation.

- **Repositories**:
  - **Abstraction**: Interface-based (e.g., `OrderRepository`, `QuoteRepository`).
  - **Dual Storage**: 
    - **In-Memory**: `Mock*Repository` (testing).
    - **MongoDB**: `Mongo*Repository` with retry logic (`MongoOperationsWithRetry`).
  - **Factory Pattern**: `RepositoryFactory` abstracts storage selection (`MEMORY` or `MONGODB`).

---

#### **2. API Endpoints & Interfaces**
| Controller | HTTP Methods | Key Endpoints | Purpose |
|------------|--------------|---------------|---------|
| `DealerController` | GET, POST, PUT, DELETE | `/dealers`, `/dealers/{name}` | Dealer CRUD |
| `OrderController` | GET, POST, PUT, DELETE | `/orders`, `/orders/{id}`, `/orders/{id}/events`, `/orders/{id}/status` | Order lifecycle, event/status updates |
| `QuoteController` | GET, POST, PUT, DELETE | `/quotes`, `/quotes/{id}` | Quote CRUD and search |
| `ShipmentController` | GET, POST, PUT, DELETE | `/shipments`, `/shipments/{id}`, `/shipments/deliveries`, `/shipments/{id}/events` | Shipment tracking, delivery aggregation |
| `PingController` | HEAD, GET | `/ping` | Health check |

---

#### **3. Database Schemas & Data Models**
- **MongoDB Collections**:
  - `dealers`: Dealer name, contact, address.
  - `orders`: Order ID, quote ID, status, events array.
  - `quotes`: Customer/dealer names, items list, cost, location.
  - `shipments`: Order ID, delivery address, events, contact info.
  - `catalog`: SKU, description, price, inventory.
- **MongoDB-Specific Models**:
  - `Dealer`, `OrderDetails`, `QuoteDetails`, `ShipmentDetails`, `CatalogItem` (distinct from core models).
- **Indexes**: Key fields (`orderId`, `quoteId`, `skuNumber`, `dealerName`) indexed for performance.

---

#### **4. Service Dependencies & Communication**
- **Controller → Repository**: 
  - Controllers use `RepositoryFactory` to access repositories.
  - Example: `OrderController` depends on `OrderRepository` and `QuoteRepository`.
- **Cross-Repository Dependencies**:
  - `OrderRepository` → `QuoteRepository` (for order creation).
  - `ShipmentRepository` → `OrderRepository` (for shipment validation).
- **Telemetry**: All controllers use `TelemetryClient` (Application Insights) for exception tracking.
- **Configuration**: Storage type (`mongodb`/`memory`) injected via `application.properties`.

---

#### **5. Key Business Logic & Algorithms**
- **Quote-to-Order Flow**: 
  - `POST /orders?fromQuote={id}` creates an order from a quote, checking for conflicts.
- **Order Status Transitions**: 
  - `PUT /orders/{id}/status` updates status with timestamped events.
- **Shipment Event Tracking**: 
  - Events appended via `/shipments/{id}/events` with validation.
- **Validation Logic**: 
  - Models validate fields (e.g., `DealerInfo.validate()` checks required fields).
  - Endpoints return 400/BAD_REQUEST for invalid data.

---

#### **6. Configuration & Deployment**
- **Spring Boot Configuration**:
  - `application.properties`: Server ports (8080/8081), MongoDB host, storage type (`mongodb`).
  - `ApplicationInsights.xml`: Telemetry setup (developer mode enabled).
- **Build Metadata**: `buildinfo.properties` tracks version/timestamp.
- **Test Configuration**: `TestOrderingConfiguration` sets up `MongoTemplate` and `RepositoryFactory` for tests.

---

#### **7. Architectural Patterns & Frameworks**
- **Repository Pattern**: Clean abstraction between controllers and data layers.
- **Factory Pattern**: `RepositoryFactory` selects storage backend at runtime.
- **Retry Logic**: `MongoOperationsWithRetry` wraps MongoDB operations with telemetry.
- **Spring MVC**: RESTful controllers with `@RequestMapping`.
- **Dependency Injection**: Autowired repositories and telemetry clients.
- **DTOs**: Core models (`Order`, `Quote`) act as data transfer objects.

---

### Microservice Decomposition Insights
1. **Bounded Contexts**:
   - **Dealer Service**: `DealerController` + `DealersRepository`.
   - **Catalog Service**: `CatalogItem` model + `CatalogItemsRepository`.
   - **Quote Service**: `QuoteController` + `QuoteRepository`.
   - **Order Service**: `OrderController` + `OrderRepository`.
   - **Shipment Service**: `ShipmentController` + `ShipmentRepository`.

2. **Database Separation**:
   - Each service should own its MongoDB collection (e.g., `orders` for Order Service).

3. **Cross-Cutting Concerns**:
   - **Telemetry**: Centralized Application Insights (instrument per service).
   - **Validation**: Common model validation logic (shared library).

4. **Inter-Service Communication**:
   - **Synchronous Calls**: Order Service → Quote Service (for order creation).
   - **Event-Driven**: Shipment updates via events (e.g., Kafka).

5. **Deployment**:
   - Each service as a standalone Spring Boot application.
   - Externalize `application.properties` per service (e.g., `order-service.properties`).

6. **Critical Observations**:
   - **Performance Test**: `DealerController.getDealers()` has intentional load (100k MongoDB calls) – optimize in microservices.
   - **Data Consistency**: Orders reference quotes; shipments reference orders – enforce via distributed transactions or sagas.
   - **Aggregates**: `ShipmentController.getDeliveries()` aggregates Quote/Order/Shipment – redesign as API composition.
